# 02: PostgreSQL Provider 骨架：装配、只读连接、列对象

**What to build:**

`SHARPDB__TYPE=postgresql` 能被识别、装配并启动。启动时用普通 Npgsql 连接串连上库；连接由引擎自己置于只读模式，因此写操作被引擎拒绝（不必用户手动加参数）。两个"列对象"的工具——列有哪些表和视图、列有哪些库——对真实 PostgreSQL 库答出与 MySQL/SQLite **同形**的结果。

这一票走完整条路径（配置 → 装配 → 连接 → 内省 → Tool → 契约测试），PostgreSQL 的引擎专属测试项目与种子 schema 也在这一票就位，后续票在它上面加内容。

**Blocked by:** 01

**Status:** resolved

- [x] 新增 PostgreSQL Provider 项目，独占 Npgsql 依赖；Core 不引用任何 Driver（沿用既有分层）。
- [x] Host 装配三个 Provider；`SHARPDB__TYPE=postgresql` 启动成功，`postgres` 仍报"未知类型"，期望类型串变为三者。
- [x] 只读由 Provider 自己加上；连接交出前引擎已处于只读模式。用一个写语句验证：**引擎**拒绝它（不是 Guard 拒绝）。
- [x] 启动探测：连不上 / 密码错 / 库不存在 → fail-fast，一行 stderr，不含连接串凭据。
- [x] `list_tables` 报出 `search_path` **可见**的表与视图、按名排序、区分表与视图；**系统 schema（`pg_catalog` / `information_schema`）的对象不出现**（实测：可见性判定会把约 64 张系统表算进来）。
- [x] `list_databases` 报出连接可见的库名；**模板库不出现**。
- [x] 新增 PostgreSQL 契约夹具（Testcontainers，pin `postgres:16`）与 PG 种子脚本；Docker 缺席时跳过而非失败。
- [x] `ProviderContractSuite` 中与"列表"有关的断言在 PostgreSQL 上通过；若某条断言暴露真实引擎分歧而非 Provider 缺陷，按既有规则移入引擎专属测试并记录。
- [x] MySQL 与 SQLite 的既有测试保持绿。

## Comments

### 2026-10-12

`feat/postgresql-provider` 的第二个提交。

**落下什么**

- 新项目 `src/SharpDb.Provider.PostgreSql`（独占 `Npgsql` 9.0.4）与 `tests/SharpDb.Provider.PostgreSql.Tests`（新增 `Testcontainers.PostgreSql` 4.16.0）。版本都进 `Directory.Packages.props`。
- `PostgreSqlDatabaseProvider`：类型名 `postgresql`；`CreateReadOnlyConnectionAsync` 开连接后立刻发 `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`（与 MySQL 同位置同形态）；`Policy` 指向本项目的 `PostgreSqlReadOnlyPolicy`。
- Host 装配三个 Provider（`ProviderCatalog` 不用改——它的期望类型串本来就是从构造参数生成的，自动变成 `"mysql" or "postgresql" or "sqlite"`）。
- `ContractSchema.PostgreSqlDdl`：共享 schema 的第三份脚本。键用 `GENERATED BY DEFAULT AS IDENTITY`，`payload` 用 `BYTEA`，`ratio` 用 `DOUBLE PRECISION`。

**实测得到的引擎事实（都是先测后写，不是从文档推的）**

- 可见性判定确实会把系统对象算进来，而且比我预想的多得多：**不加 schema 过滤是 140 行**，加过滤后正是共享 schema 的 7 个对象。spec 里记的"约 64"是探针阶段的早期数目，实际更糟。
- `format_type(atttypid, atttypmod)` 一次给出 `character varying(50)` 这样的完整声明；`attidentity` 为 `'d'` 表示 `GENERATED BY DEFAULT AS IDENTITY`。
- 视图列**不传播**基表约束：`active_users` 的两列 `attnotnull` 都是 `f`。这就是 spec 记的那条真实分歧。
- `pg_constraint` 的 `conkey`/`confkey` 是平行数组，`unnest(conkey, confkey) WITH ORDINALITY` 让第 n 个本地列对上第 n 个引用列 —— 复合外键的配对只有这里拿得到。实测 `bookings` 给出 `conkey={2,3}`、`confkey={2,1}`。
- 复合主键 `conkey` 顺序即键序：`(b, a)` 报 `{b,a}`，不是声明序。
- `pg_index.indisprimary` 是排除主键索引的判据（PG 的索引名是 `表名_pkey`，名字不可靠）。
- `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY` 跨事务有效（实测：另起一条 `INSERT` 被拒）。`SET SESSION TRANSACTION READ ONLY` 在 `psql -c` 下看着像生效，但那是同一事务块内的假象——spec 说它跨事务无效，实测确实如此。
- 只读会话**挡不住** `pg_read_file`（读到 30050 字节的配置文件）与 `pg_ls_dir`（列出 24 项）。票 05 的禁用表因此是必须的，不是锦上添花。

**三个只有真库才暴露的坑（都是我写错、测试抓到的）**

1. **`uint` 参数 Npgsql 拒绝发送** —— `oid` 列是 `uint`，`parameter.Value = oid` 抛 `InvalidCastException: Writing values of 'System.UInt32' is not supported`。补 `DbType.UInt32` 又抛 `NotSupportedException: The parameter type DbType.UInt32 isn't supported`。只有驱动自己的类型能用：`new NpgsqlParameter("oid", NpgsqlDbType.Oid) { Value = oid }`。
2. **`"char"` 列不能按 string 读** —— `attidentity`、`confdeltype`、`confupdtype` 都是 PG 内部的单字节 `"char"`，`reader.GetString(...)` 抛 `InvalidCastException: Reading as 'System.String' is not supported for fields having DataTypeName 'char'`。修法是在 SQL 里 `::text`。
3. **名称匹配少了一种填法** —— 我第一版只写 `c.relname = lower(@table)`，于是 `MixedCase` 这种引号建的表永远查不到（引擎专属测试 `DescribeTable_reports_the_name_the_catalogue_spells` 抓到的）。改成 `(c.relname = @table OR c.relname = lower(@table))`，并按"精确匹配优先"排序：未引号写法折叠到小写能命中，引号写法原样也能命中，两者都存在时以原样为准。

**为什么引擎专属项目这一票就建起来**

spec 说契约测试的验收面就是"同一组断言跑三遍"。但共享套件只能装下**三个引擎都答得一样**的东西，凡是引擎自己的行为就必须有地方钉住。所以本票把 PostgreSQL 专属项目连同夹具一起建了起来，并放了 9 条只属于这个引擎的断言（`serial`/`bigserial` 自增、视图不传播约束及其基表对照、类型声明完整、大小写两种匹配、系统 schema 与模板库的排除）。后续票往这里加内容，不用再改项目结构。

**新增/调整的断言**

- `StartupContractTests`：期望类型串断言加 `"postgresql"`；`postgres` 仍是"未知类型"示例（这条没动，正好锁住 spec 的要求）。新增两条：类型名大小写不敏感（`PostgreSQL` 被接受并走到连接阶段）、启动失败消息不含密码（脱敏 tripwire）。
