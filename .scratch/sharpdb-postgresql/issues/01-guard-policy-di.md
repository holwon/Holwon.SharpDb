# 01: Guard 改造为策略驱动的 DI 服务

**What to build:**

Guard 不再是一个用 `GenericDialect` 解析、写死四个 MySQL 函数名的静态类。它变成一个由**被选中 Provider 提供的只读策略数据**构造的 Core 服务，策略数据只有两项：**方言**与**禁用函数表**。MySQL 与 SQLite 的策略就是它们今天的行为，因此这次改造**不改变任何既有行为**——只是把"哪个引擎用什么策略"从写死变成由 Provider 声明。

这是"让改动变简单"的那一步，也是本特性的唯一结构性改动：先落地它并保持全绿，PostgreSQL 的票才有可能只写 Provider。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] Guard 是 Core 里一个可注入的服务，由策略数据构造；工具通过注入取得它，而不是静态调用。
- [ ] 策略数据只含两项：一个方言枚举值、一组禁用函数名；**不引入对 SQL parser 的依赖**（方言以枚举表达，parser 仍只留在 Core）。
- [ ] MySQL 与 SQLite 各自声明自己的策略：方言取"通用"，禁用函数表保持今天那四个名字。
- [ ] 既有 Guard 测试改为按策略断言，且全部覆盖 **MySQL 与 SQLite 两套策略**。
- [ ] 共享契约套件里的工具构造入口改为接受策略；三个既有测试程序集全部保持绿（MySQL 与 SQLite 的契约测试一条不改、一条不红）。
- [ ] 反引号标识符仍被放行（锁住"不回归 MySQL"）；一个只读语句在被误拒的方言下仍被拒（锁住"策略数据真的在起作用"）。
- [ ] 不改 Provider 契约的既有成员语义；不放宽许可清单——策略只能**加**禁用函数，不能删改放行规则。
