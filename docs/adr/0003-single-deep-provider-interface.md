# Provider 是一个深接口，而不是多个小 seam

每种数据库类型实现**单个** `IDatabaseProvider`，把连接创建、方言与内省全部收在它后面；不拆成 `IDbConnectionFactory` + `ISchemaIntrospector` + `ISqlDialect` 三个 seam。

理由是这些部分从不独立变化——不存在"MySQL 的连接工厂 + SQLite 的内省器"这样的组合，拆开只会换来多个注册点、多个生命周期和一个没有消费者的组合问题，却没有多一分杠杆。MySQL 与 SQLite 确实是两个 adapter，但它们落在**同一个** seam 上。Provider 的实现内部仍可自行分层，那只是实现细节，不进接口。

## 2026-10 修订：契约新增"策略数据"，结论不变

加入 PostgreSQL 时接口多了**一个**成员：`ReadOnlyPolicy Policy { get; }`，内容是两项数据——该引擎的方言（枚举值）与一组禁用函数名。

**结论不变，理由反而更硬了。** 方言确实因引擎而异（见 ADR 0005 的修订：PostgreSQL 方言能读 `FILTER (WHERE …)`，通用方言不能；而 PostgreSQL 方言**不认反引号**，MySQL 的 SQL 全靠它），所以"方言"这个维度第一次有了真实的变异。但**它没有变成第二个 seam**：变化的是这个 seam 携带的数据，接口仍然只有一个，装配点仍然只有一个，新增数据库类型仍然只需实现一个接口。三个 seam 方案要解决的问题（"连接方式与内省方式独立组合"）依然不存在。

**没有采纳的形态**，两条都试想过：

- **给每个 Provider 一个 Guard 子类、允许它 `override` 放宽策略。** 否决理由写在 ADR 0013：Guard 唯一的安全性质是许可清单，"拒绝永远安全、错误只表现为误拒"这条**集中保证**会被降级成逐实现保证。
- **新建 `Core.Abstractions` 之类的项目来放策略数据。** 那是为将来某种"每 Provider 需要不同 Guard 算法"预留的形态；今天没有任何 Provider 需要（实测 43 条语句在两方言下分类完全一致），提前建它正是本 ADR 反对的"先声明后用不到的东西"。

策略数据因此放在既有的契约项目里，且**不引入 parser 依赖**——方言以枚举表达，枚举到 parser 方言的映射留在 Core（ADR 0005 修订）。

**"这些部分从不独立变化"这句话要跟着改一句。** 原话说"这些部分"包含方言，而现在方言以数据形式进了接口。更准确的表述是：**接口的成员不因引擎而分叉**——每个 Provider 都回答同样的问题（你的类型名是什么、你的只读策略是什么、怎么开只读连接、怎么内省），只是答案不同。这与"拆成多个 seam"不是同一件事。
